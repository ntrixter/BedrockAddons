# catalog.json

`catalog.json` is a small machine-readable index of every add-on in this
repository and its latest releases. It exists so a consumer — an add-on
manager, an update checker, a script — can resolve "the latest version of
add-on X" reliably.

Fetch it from `raw.githubusercontent.com`, unauthenticated:

```
https://raw.githubusercontent.com/ntrixter/BedrockAddons/main/catalog.json
```

It is regenerated by the release workflow and committed back to `main`, so it
is always current as of the last release.

## Why not the Releases API

**`/releases/latest` does not work here.** That endpoint is repo-wide, and this
repository releases many add-ons independently, so "latest" means whichever
add-on happened to be tagged most recently. It will confidently return a
release for a different add-on than the one you asked about.

If you use the Releases API instead of this catalog, you must list releases and
filter by the `<addon-id>-v` tag prefix yourself.

**If you do fall back to the API, use conditional requests.** Send the `ETag`
from your previous response as `If-None-Match`. A `304 Not Modified` does not
count against the unauthenticated rate limit, so polling stays cheap:

```
GET /repos/ntrixter/BedrockAddons/releases
If-None-Match: "e0f8...c31"
```

## Schema

```json
{
  "schema_version": 1,
  "generated_at": "2026-01-31T12:00:00Z",
  "repository": "ntrixter/BedrockAddons",
  "addons": {
    "sleep-addon": {
      "display_name": "Sleep",
      "description": "One player sleeping skips the night.",
      "deprecated": false,
      "latest_stable": {
        "version": "1.2.0",
        "tag": "sleep-addon-v1.2.0",
        "filename": "sleep-addon-1.2.0.mcaddon",
        "download_url": "https://github.com/ntrixter/BedrockAddons/releases/download/sleep-addon-v1.2.0/sleep-addon-1.2.0.mcaddon",
        "sha256": "9f86d081884c7d659a2feaa0c55ad015a3bf4f1b2b0b822cd15d6c15b0f00a08",
        "published_at": "2026-01-31T11:58:03Z",
        "min_engine_version": [1, 21, 0],
        "packs": [
          {
            "uuid": "4f9a2c18-6b3d-4e11-9c77-2a1b8de5f003",
            "type": "data",
            "version": [1, 2, 0],
            "folder": "sleep-addon_BP"
          }
        ]
      },
      "latest_prerelease": null
    }
  }
}
```

### Top level

| Field | Type | Meaning |
| --- | --- | --- |
| `schema_version` | integer | Currently `1`. Bumped only for a breaking change to this shape. Check it and refuse to parse a version you do not understand. |
| `generated_at` | string | ISO 8601 UTC timestamp of the last regeneration. |
| `repository` | string | `owner/repo`, so a consumer can build API URLs without hard-coding them. |
| `addons` | object | Keyed by add-on ID. The key is also the tag prefix, the issue label, and the artifact filename stem. |

### Add-on entry

| Field | Type | Meaning |
| --- | --- | --- |
| `display_name` | string | Human-readable name. Falls back to the add-on ID if none is set. |
| `description` | string | One short sentence. May be empty. |
| `deprecated` | boolean | `true` once the add-on is retired. Existing installs keep working; do not offer it as a new install. |
| `latest_stable` | object \| null | Highest released version with no prerelease suffix. |
| `latest_prerelease` | object \| null | Highest released version *with* a prerelease suffix. |

Stable and prerelease are kept apart so a consumer can offer a stable-only
channel by default. Whether a release is a prerelease is decided by the
version, not by a branch: `1.5.0-beta.1` is a prerelease, `1.5.0` is not.

`latest_prerelease` is not necessarily newer than `latest_stable`. It is simply
the highest prerelease that exists, which may predate the current stable
release. Compare versions before offering it as an upgrade.

### Release object

| Field | Type | Meaning |
| --- | --- | --- |
| `version` | string | Semver, e.g. `1.2.0` or `1.5.0-beta.1`. |
| `tag` | string | `<addon-id>-v<version>`. |
| `filename` | string \| null | The single downloadable asset. |
| `download_url` | string \| null | Direct download for that asset. |
| `sha256` | string \| null | Hex digest of the asset. Verify it after downloading. |
| `published_at` | string \| null | ISO 8601 UTC. |
| `min_engine_version` | array \| null | Three integers, the highest across the add-on's packs. Skip the add-on if the installed Bedrock version is older. |
| `packs` | array | One entry per pack in *this version*. |

`min_engine_version` and `packs` live inside the release object rather than on
the add-on, because both can change between versions: a release can add a
resource pack, or raise the Minecraft version it needs. Read them from the
release you are actually about to install.

### Pack entry

| Field | Type | Meaning |
| --- | --- | --- |
| `uuid` | string | The pack's **header** UUID. This is the `pack_id` that goes in `world_behavior_packs.json` / `world_resource_packs.json`. |
| `type` | string | `data` for a behaviour pack, `resources` for a resource pack. Read from `modules[].type` in the manifest. |
| `version` | array | Three integers, the pack version, in the array form the world JSON files expect. |
| `folder` | string | The recommended directory name on a server, e.g. `sleep-addon_BP`. |

`packs` is the part that matters for update detection. **Compare the installed
pack UUID and version against this array, not against release tags.** A
consumer also needs `type` to decide which server directory a pack belongs in
(`behavior_packs/` or `resource_packs/`) and which world JSON file to register
it in.

`folder` is a recommendation, not a promise about the archive. In a `.mcaddon`
it matches the folder inside the archive. A single-pack `.mcpack` extracts
loose with `manifest.json` at the top level, so the consumer creates that
folder itself. The server resolves packs by the UUID in the manifest, not by
folder name, so the name is free to be descriptive.

## Null releases are a normal state

An add-on can exist in this repository before it has ever been released, and
may never have a prerelease at all. In both cases the entry is present with
`latest_stable` and/or `latest_prerelease` set to `null`.

**This is a published state, not a transient one.** A consumer must handle it:
show the add-on if it is useful to, but treat it as having nothing to download.
Do not assume `latest_stable` is an object.

An add-on with no releases yet still carries a real `display_name`,
`description` and `deprecated` flag.

## Empty catalog

Before any add-on exists, the catalog is valid and empty:

```json
{
  "schema_version": 1,
  "generated_at": "2026-01-31T12:00:00Z",
  "repository": "ntrixter/BedrockAddons",
  "addons": {}
}
```

## Validating

CI checks the committed catalog against this schema on every pull request, so a
malformed catalog fails the build rather than breaking a consumer silently:

```sh
python3 scripts/gen_catalog.py --validate catalog.json
```
